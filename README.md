# SkillBarter

## Запуск готового сайта

Нужен **Node.js 22 или новее**. В корне проекта выполните:

```bash
npm start
```

Откройте [http://localhost:3000](http://localhost:3000). Панель администратора находится по адресу [http://localhost:3000/admin](http://localhost:3000/admin). База SQLite создаётся автоматически в `data/` и сохраняет данные между запусками. Дополнительные пакеты устанавливать не нужно.

Для демонстрации при первом запуске создаются аккаунты:

| Роль | Почта | Пароль |
|---|---|---|
| Пользователь | `aiaru@skillbarter.local`, `symbat@skillbarter.local`, `bayansulu@skillbarter.local` или `almas@skillbarter.local` | `Demo12345!` |
| Администратор | `admin@skillbarter.local` | `Admin12345!` |

Перед первым запуском пароли можно изменить через переменные окружения `DEMO_PASSWORD` и `ADMIN_PASSWORD`. Для реального размещения обязательно задайте собственный `ADMIN_PASSWORD`; демонстрационные учётные записи предназначены для локальной проверки.

Чтобы управлять ролями, войдите как `admin@skillbarter.local`, откройте `/admin` → **Участники**. Там можно создать аккаунт сразу с ролью администратора или назначить администратором уже зарегистрированного пользователя. Сменённая роль вступает в силу после повторного входа; действие фиксируется в журнале. Пользователь при обычной регистрации не может выбрать роль администратора.

Карточка услуги открывается нажатием на любую её область. Иллюстрации категорий находятся в `public/images/`. Для выбора личной аватарки откройте **Мой профиль → Выбрать аватарку** и загрузите PNG, JPEG или WebP до 10 МБ. После обрезки до квадрата файл сохраняется в `data/avatars/`, а ссылка на него — в базе данных.

Проверка ключевого сценария: `npm test`. Тест создаёт отдельную временную базу, проводит обмен минутами, проверяет роли, отзыв и спор. Используется встроенный в Node.js модуль SQLite; в версии Node.js 22 он может выводить предупреждение об экспериментальном статусе.

## Техническое задание
## 1. Общие сведения о проекте

**Название:** SkillBarter — платформа обмена навыками и временем.

**Тип проекта:** адаптивное веб-приложение.

**Продолжительность разработки:** 7 недель.

**Команда:** 4 человека.

**Язык интерфейса:** русский.

**Цель:** создать платформу, на которой пользователи помогают друг другу и оплачивают услуги внутренними часами без денежных платежей.

Основной принцип:

> Один час оказанной помощи позволяет получить один час помощи другого участника.

Стоимость часа не зависит от категории или квалификации исполнителя. Занятие программированием продолжительностью 60 минут и занятие английским продолжительностью 60 минут стоят одинаковое количество времени.

**Пример обмена:**

1. Айару проводит для Сымбат занятие по Java длительностью 60 минут.
2. После подтверждения занятия 60 минут переходят с баланса Сымбат на баланс Айару.
3. Айару использует полученные минуты для занятия по дизайну у Баянсулу.

Прямой взаимный обмен между двумя людьми необязателен.

## 2. Задачи проекта

Приложение должно позволять:

- создавать профиль и указывать навыки;
- публиковать предложения помощи;
- находить услуги по категориям и фильтрам;
- отправлять и принимать заявки;
- согласовывать время встречи;
- резервировать и переводить внутренние минуты;
- общаться внутри заявки;
- подтверждать выполнение услуги;
- оставлять отзывы;
- рассматривать спорные ситуации;
- просматривать историю обменов и операций.

**Результат разработки:** работающий сайт с базой данных, авторизацией и полным сценарием обмена — от публикации услуги до перевода минут и отзыва.

## 4. Роли пользователей

### Гость

Может просматривать главную страницу, каталог, предложения и публичные профили.

Для отправки заявки, добавления в избранное и участия в обмене должен войти в аккаунт.

### Зарегистрированный пользователь

Может выступать одновременно заказчиком и исполнителем.

Ему доступны:

- редактирование своего профиля;
- управление собственными предложениями;
- создание и обработка заявок;
- переписка по принятым заявкам;
- просмотр баланса и истории операций;
- подтверждение выполнения;
- отзывы и открытие споров.

### Администратор

Может:

- скрывать предложения и отзывы;
- блокировать пользователей;
- управлять категориями;
- рассматривать споры;
- просматривать связанные операции и историю событий.

Роль администратора назначается отдельно. Пользователь не может выбрать её при регистрации.

В MVP ручное изменение баланса администратором лучше исключить: для демонстрации достаточно возврата или перевода резерва при рассмотрении спора.

## 5. Правила внутреннего баланса

### 5.1. Единица расчёта

Баланс хранится **целым числом минут**.

Для MVP предлагается:

- минимальная длительность услуги — 30 минут;
- максимальная длительность — 240 минут;
- шаг длительности — 30 минут.

Исполнитель задаёт допустимый диапазон внутри этих ограничений.

### 5.2. Стартовые минуты

После регистрации создаётся кошелёк и начисляется **120 минут**.

Начисление выполняется один раз. Создание кошелька и запись бонуса должны быть согласованной операцией: повтор запроса не создаёт второй бонус.

### 5.3. Доступный баланс и резерв

Кошелёк содержит:

- **доступные минуты** — можно потратить;
- **зарезервированные минуты** — закреплены за принятыми заявками.

Пример для услуги длительностью 60 минут:

| Состояние | Доступно заказчику | В резерве заказчика | Изменение баланса исполнителя |
|---|---:|---:|---:|
| До принятия заявки | 120 | 0 | 0 |
| После принятия | 60 | 60 | 0 |
| После завершения | 60 | 0 | +60 |
| При отмене вместо завершения | 120 | 0 | 0 |

**При завершении минуты списываются из резерва. Повторного списания с доступного баланса нет.**

### 5.4. Обязательные ограничения

- Баланс не может стать отрицательным.
- Нельзя передать минуты самому себе.
- Все операции выполняются на сервере.
- Каждая операция записывается в журнал.
- Повторное нажатие кнопки не приводит к повторному переводу.
- Перевод между пользователями не создаёт новые минуты.
- Во время спора резерв сохраняется до решения администратора.

Поскольку до принятия заявки минуты не резервируются, **сервер повторно проверяет баланс именно в момент принятия**. Если заказчик уже потратил минуты, принятие не выполняется.

## 6. Жизненный цикл заявки

В исходном ТЗ состояния «Создана» и «Ожидает ответа» фактически дублируют друг друга. Для MVP достаточно следующей модели:

| Статус | Значение | Кто запускает переход |
|---|---|---|
| `PENDING` | Заявка отправлена и ожидает ответа | Заказчик |
| `ACCEPTED` | Время согласовано, минуты зарезервированы | Исполнитель |
| `AWAITING_CONFIRMATION` | Исполнитель сообщил об оказании услуги | Исполнитель |
| `COMPLETED` | Заказчик подтвердил услугу, минуты переведены | Заказчик |
| `REJECTED` | Исполнитель отклонил заявку | Исполнитель |
| `CANCELLED` | Заявка отменена | Участник по правилам отмены |
| `DISPUTED` | Открыт спор, резерв удерживается | Любая сторона |
| `RESOLVED` | Спор рассмотрен, решение исполнено | Администратор |

Решение по спору хранится отдельно: **возврат заказчику** или **перевод исполнителю**.

Статусы «Выполняется» и «Просрочена» для первой версии необязательны. Интерфейс может показывать, что время встречи наступило, без отдельного изменения статуса в базе.

### Правила отмены и подтверждения

1. Ожидающую заявку заказчик может отменить без операций с балансом.
2. Принятую заявку любая сторона может отменить до начала встречи с полным освобождением резерва.
3. После начала встречи односторонняя отмена недоступна: при проблеме открывается спор.
4. Исполнитель отмечает услугу оказанной после запланированного окончания встречи.
5. Заказчик подтверждает выполнение или открывает спор.
6. Если заказчик не отвечает, исполнитель может открыть спор через 48 часов после запроса подтверждения.
7. Автоматический перевод минут при молчании заказчика в MVP не выполняется.

Исполнитель подтверждает выполнение кнопкой «Услуга оказана», заказчик — кнопкой «Подтвердить». Это и составляет подтверждение обеими сторонами.

## 7. Функциональные требования

### 7.1. Авторизация и профиль

Регистрация: имя, уникальная почта, пароль.

Профиль:

- имя и инициалы вместо обязательной загрузки аватара;
- город;
- описание;
- языки общения;
- навыки;
- формат помощи;
- рейтинг;
- количество успешно завершённых обменов.

Почта и другие непубличные данные не отображаются в публичном профиле.

### 7.2. Предложения

Обязательные поля:

- название и описание;
- категория;
- уровень;
- язык;
- формат;
- город для офлайн-услуг;
- минимальная и максимальная длительность.

Владелец может редактировать и отключать предложение. Если по нему уже существуют заявки, предложение архивируется, чтобы сохранить историю.

В заявке фиксируются согласованные название услуги, длительность и формат. Последующее редактирование предложения не меняет условия существующего обмена.

### 7.3. Каталог

Для MVP реализуются:

- поиск по названию и описанию;
- фильтры по категории, городу, формату и языку;
- сортировка по новизне и рейтингу;
- пагинация;
- добавление в избранное.

### 7.4. Заявки и расписание

Заказчик выбирает длительность, дату, время и формат.

Исполнитель принимает предложенное время либо отклоняет заявку с пояснением. Для MVP сложный механизм встречных предложений не требуется: заказчик может отправить новую заявку.

Перед принятием сервер проверяет отсутствие пересечений **у обоих участников**.

Встречи 15:00–16:00 и 15:30–16:30 конфликтуют. Встречи 15:00–16:00 и 16:00–17:00 — нет.

Сама проверка должна оставаться корректной при одновременном принятии двух заявок.

### 7.5. Чат и уведомления

Чат создаётся при принятии заявки и доступен только её участникам. Администратор получает доступ к связанным сообщениям при рассмотрении спора.

В MVP поддерживаются:

- текст;
- время отправки;
- системные сообщения;
- периодическое обновление переписки.

Текст отображается без выполнения пользовательского HTML.

Уведомления создаются при получении заявки, принятии, отклонении, отмене, запросе подтверждения, завершении и событиях спора.

### 7.6. Отзывы

Отзыв разрешён только после обычного завершения заявки со статусом `COMPLETED`.

Ограничения:

- оценка от 1 до 5;
- один отзыв от каждой стороны;
- получателем является второй участник;
- нельзя оценить себя;
- скрытые администратором отзывы не участвуют в рейтинге.

### 7.7. Споры

Пользователь указывает причину и описание проблемы.

Администратор видит:

- участников;
- условия заявки;
- переписку;
- историю статусов;
- размер резерва.

В MVP предусмотрены два решения:

1. Вернуть весь резерв заказчику.
2. Перевести весь резерв исполнителю.

Решение, его причина, автор и время сохраняются. Повторное исполнение решения не должно повторно перемещать минуты.

## 8. Техническая организация

Предлагаемый основной стек:

| Область | Технологии |
|---|---|
| Интерфейс и сервер | Next.js, React, TypeScript |
| Стили | Tailwind CSS |
| Формы и проверка данных | React Hook Form, Zod |
| База данных | PostgreSQL |
| Работа с БД | Prisma |
| Авторизация | Auth.js с отдельно реализованной регистрацией и хешированием паролей |
| Модульные тесты | Vitest |
| Пользовательские тесты | Playwright |

**Redis, S3, почтовый сервис и постоянные соединения чата не являются обязательными зависимостями MVP.**

Бизнес-логика размещается в отдельных серверных модулях. Обработчики API проверяют входные данные и права, затем вызывают эти модули.

Все изменения баланса проходят через единый сервис кошелька. Остальные модули не меняют его поля напрямую.

### Дополнения к модели данных

К исходным таблицам необходимо добавить или уточнить:

| Модель | Что уточнить |
|---|---|
| `Wallet` | Один кошелёк на пользователя; неотрицательные доступный баланс и резерв |
| `WalletTransaction` | Изменения доступного баланса и резерва отдельно; общий идентификатор операции |
| `ExchangeRequest` | Время окончания, снимок условий, время запроса подтверждения |
| `RequestEvent` | История переходов статусов и действий участников |
| `AuditLog` | Действия администратора и причины решений |
| `Review` | Уникальная пара «заявка + автор» |
| `Favorite` | Уникальная пара «пользователь + предложение» |
| `Conversation` | Не более одного чата на заявку |

Для завершения заявки нужны **два разных действия API**: отметка исполнителя об оказании услуги и подтверждение заказчика. Один неоднозначный endpoint `/complete` лучше заменить на `/mark-done` и `/confirm`.

- чата и API сообщений;
- списка уведомлений;
- формы отзывов и расчёта рейтинга.

**Основные модели:** `Skill`, `UserSkill`, `Conversation`, `Message`, `Notification`, `Review`.

**Дополнительно:** готовит дизайн-систему и макеты ключевых страниц. Остальные участники самостоятельно собирают свои страницы из общих компонентов.

**Тестирует:** доступ к чужому чату, повторный отзыв, отзыв до завершения, пересчёт рейтинга.

**Результат:** участники имеют профили, общаются, получают уведомления и оставляют отзывы.

### 9.4. Кобеев Алмас — заявки, расписание и споры

**Пишет код:**

- создания заявки;
- страницы заявки и списка входящих/исходящих заявок;
- правил перехода между статусами;
- принятия, отклонения и отмены;
- проверки пересечений встреч;
- списка ближайших встреч;
- отметки об оказании услуги и подтверждения;
- открытия спора;
- административного рассмотрения споров;
- базовой модерации пользователей и предложений.

**Основные модели:** `ExchangeRequest`, `RequestEvent`, `Dispute`, `AuditLog`.

**Тестирует:** запрещённые переходы, действия постороннего пользователя, конфликт времени, повторное решение спора.

**Результат:** полный жизненный цикл обмена от заявки до завершения либо решения спора.

**Граница ответственности с Айару:** Алмас управляет сценарием заявки, Айару реализует операции кошелька. Изменение статуса и перемещение минут выполняются в одной транзакции БД.

## 10. План на семь недель

| Неделя | Айару | Сымбат | Баянсулу | Алмас |

| **2. Аккаунты и услуги** | Регистрация, вход, кошелёк, стартовый бонус | Создание и редактирование предложений | Редактирование профиля и навыков | Создание заявки и списки заявок |
| **3. Первый обмен** | Резервирование и освобождение минут | Поиск, фильтры, страница предложения | Чат: хранение и отправка сообщений | Принятие, отклонение, отмена, конфликты времени |

**Контрольные точки:**

- конец 2-й недели — регистрация, профиль и публикация услуги;
- конец 3-й — заявка принимается, минуты резервируются;
- конец 4-й — обмен полностью завершается;
- конец 5-й — работают отзывы и споры;
- 6–7-я недели — исправления, публикация и защита.

На последней неделе новые крупные функции не добавляются.

## 11. Организация совместной разработки

### Репозиторий и ветки

Один общий репозиторий. Основная ветка `main` должна оставаться рабочей.

Для каждой задачи создаётся отдельная ветка:

```text
feature/auth-registration
feature/offers-search
feature/request-chat
feature/request-confirmation
```

Изменения объединяются через Pull Request после проверки другим участником.

### Правила команды

1. Каждая задача имеет ответственного и критерий готовности.
2. Каждый участник делает коммиты со своей учётной записи.
3. Коммит содержит законченное изменение, например `feat: add offer filters`.
4. Изменения общей схемы БД согласуются до создания миграций.
5. Секреты не попадают в репозиторий; список переменных хранится в `.env.example`.
6. Каждый участник проверяет свой модуль и исправляет его ошибки.
7. Раз в неделю команда показывает работающий общий сценарий.

**Готовность задачи:** интерфейс подключён к реальным данным, сервер проверяет права и входные значения, ошибки отображаются пользователю, код проходит проверку типов и сборку.

Чтобы участники не ждали друг друга, на первой неделе нужно согласовать поля данных и форматы ответов API. До готовности API страницы можно делать на временных данных с той же структурой.

## 12. Критерии приёмки проекта

MVP считается готовым, когда проверены следующие сценарии:

| Проверка | Ожидаемый результат |
|---|---|
| Регистрация | Создан аккаунт и однократно начислены 120 минут |
| Публикация услуги | Предложение появляется в каталоге |
| Заказ собственной услуги | Сервер отклоняет действие |
| Принятие заявки | Минуты переходят в резерв |
| Недостаточный баланс | Принятие не выполняется |
| Одновременные заявки | Нельзя зарезервировать больше доступного баланса |
| Пересечение встреч | Вторая конфликтующая встреча не принимается |
| Повторный запрос | Нет повторного списания или начисления |
| Чужой чат | Доступ запрещён |
| Подтверждение услуги | Резерв переводится исполнителю один раз |
| Отмена до встречи | Резерв возвращается в доступный баланс |
| Отзыв до завершения | Публикация запрещена |
| Спор | Минуты удерживаются до решения |
| Решение администратора | Выполняется один раз и записывается в журнал |
| Телефон и компьютер | Основные страницы и формы работают |
| Сборка | Нет ошибок типов и сборки |

## 13. Сценарий защиты

Для демонстрации подготовить два обычных аккаунта и аккаунт администратора.

1. Показать регистрацию и стартовые 120 минут.
2. Опубликовать услугу по Java.
3. Найти её со второго аккаунта.
4. Отправить заявку на 60 минут.
5. Принять заявку и показать резерв.
6. Отправить сообщения.
7. Отметить услугу оказанной и подтвердить выполнение.
8. Показать баланс и историю обеих сторон.
9. Оставить отзыв.
10. **Создать отдельную заявку** для демонстрации спора.
11. Открыть спор и разрешить его из административной панели.

Каждый участник объясняет свой модуль, показывает написанный код и соответствующие коммиты. Это позволит продемонстрировать и работающий продукт, и личный вклад всех четырёх разработчиков.
